# Project Guidelines for AI Agents

This document outlines guidelines for AI agents (like Mistral Vibe) working on this repository.

## Git Commit Strategy

### Atomic Commits

**Prefer atomic commits** - Each commit should represent a single logical change:

- **One file or related file group per commit** - If you modify `Database.php` and `User.php` for the same feature, that's one commit. If you add a new feature file, commit it separately.
- **Clear, focused messages** - Describe what changed and why, not how.

**Good commit messages:**
```
Add User model with authentication

- Create includes/User.php with login/logout methods
- Add password hashing with password_hash()
- Include session management
```

**Bad commit messages:**
```
Fixed stuff

Added some files and changed others
```

### Commit Message Format

- Use the **imperative mood** ("Add feature" not "Added feature")
- First line: 50 characters or less, summarizing the change
- Blank line
- Optional body: more details, each line wrapped at 72 characters
- **Do NOT include** AI co-authorship attribution (e.g., "Generated by Mistral Vibe" or "Co-Authored-By: Mistral Vibe")

### What NOT to Include in Commits

- **No AI attribution** - Do not add "Generated by Mistral Vibe", "Co-Authored-By", or any AI-related tags to commit messages
- **No placeholder comments** - Remove comments like `// TODO`, `// FIX ME`, `// temp` before committing
- **No debug code** - Remove `var_dump()`, `die()`, `dd()` statements
- **No hardcoded credentials** - Use environment variables or config files

## Code Standards

### PHP

- Use **type hints** for properties, parameters, and return types
- Follow **PSR-12** coding standard where applicable
- Use **Prepared Statements** for all database queries (never concatenate SQL)
- **Escape output** with `htmlspecialchars()` when displaying user content
- **Hash passwords** with `password_hash()` and verify with `password_verify()`

### File Organization

> This is `stage-0-flat-script`: there is no `includes/`, `views/`, or `docs/` split yet. Everything lives in `index.php`. See `stage-1-basic-mvc` and `main` for the later stages where this organization applies.

- **Everything**: `index.php` (DB connection, request handling, HTML output)
- **Configuration**: `config.php` in root

### Naming Conventions

- **Classes**: `PascalCase` (e.g., `Database`, `UserModel`)
- **Methods**: `camelCase` (e.g., `getAll()`, `createPost()`)
- **Variables**: `camelCase` (e.g., `$userName`, `$postTitle`)
- **Constants**: `UPPER_SNAKE_CASE` (e.g., `DB_HOST`, `SITE_NAME`)
- **Files**: `PascalCase.php` for classes, `snake_case.php` for others

## Security Requirements

### Database

- **Always use prepared statements** with parameter binding
- **Never concatenate** user input into SQL queries
- Use **PDO** with `ATTR_EMULATE_PREPARES => false`

### Authentication

- **Hash passwords** with `password_hash()` (using `PASSWORD_DEFAULT`)
- **Verify passwords** with `password_verify()`
- **Use sessions** securely with `session_start()` and proper session management

### Output

- **Always escape** dynamic content with `htmlspecialchars()` when outputting to HTML
- Use `nl2br()` for preserving line breaks in user content
- **Never trust** user input - validate and sanitize

## Documentation

- **Update README.md** when adding new features or changing setup
- **Add to docs/** for detailed explanations (architecture, patterns, etc.)
- **Keep commit messages** descriptive enough to understand changes without reading code

## Testing

Before pushing changes:

1. **Test locally** - Ensure the application runs without errors
2. **Check SQL** - Verify all queries work with the database schema
3. **Validate forms** - Test login, logout, and any data submission
4. **Review output** - Ensure proper escaping prevents XSS

## Workflow

1. **Read existing code** before making changes
2. **Follow existing patterns** and style
3. **Test changes** locally
4. **Commit atomically** with clear messages
5. **Push and verify** on GitHub
